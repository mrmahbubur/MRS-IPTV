# BUILD — the real system, start to finish

This is the build and operations manual: the exact order of commands to take the
repository to a paying production service, wire it into your existing site backend, make
payment verification automatic, and keep yourself in full control of everything.

Read it top to bottom the first time. Every part ends with **Verify** (a command whose
output you can look at) and **If it fails** (what to do). Nothing here is aspirational —
every file, command, env var and endpoint named below exists in this repository.

Parts 1–3 are the server. Part 4 connects your site. Part 5 makes money automatic.
Part 6 makes everything else automatic. Part 7 is your control panel. Part 8 is go-live.
Part 9 is what you do in month two. Part 10 is when you outgrow one machine.

---

## Part 0 — Decisions to make before you type anything

You need three answers. Write them down; they become env values.

| Decision | Choose | Consequence |
|---|---|---|
| **Deployment shape** | `embedded` (billing inside your existing Node site) or `sidecar` (separate process on 127.0.0.1) | Embedded = one process, one deploy. Sidecar = your site can be anything (PHP, Python, Go) and billing can restart independently. Both are fully supported. |
| **Payment rail** | `bkash-api`, `nagad-api`, `own-middleware`, or `manual` | `manual` needs a human per payment; the other three are automatic. You can start manual and switch later without code changes — it is one env var. |
| **Ownership of customer email** | `billing-sends` or `your-site-sends` | Billing can send the activation code itself (SMTP), or return the plaintext code to your backend so your existing mailer sends it. Both are implemented. |

Defaults if you are unsure: **sidecar**, **manual first then bKash API**, **billing-sends**.

## Part 1 — Server

Ubuntu 22.04 or 24.04, 2 vCPU / 2 GB is enough for tens of thousands of subscribers.

### 1.1 Base system

```bash
# as root
adduser --system --group --home /var/lib/mrs-site --shell /usr/sbin/nologin mrs
apt update && apt -y upgrade
apt -y install curl ca-certificates ufw nginx sqlite3 fail2ban unattended-upgrades
timedatectl set-timezone Asia/Dhaka

# Node 20 LTS
curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
apt -y install nodejs
node -v    # expect v20.x

# firewall: only SSH and HTTP(S) reach the box
ufw default deny incoming
ufw default allow outgoing
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
ufw status
```

**Verify:** `ufw status` shows 22/80/443 allowed, everything else denied.

### 1.2 Directories and permissions

```bash
install -d -o mrs -g mrs -m 750 /var/lib/mrs-site          # database, backups, uploads
install -d -o mrs -g mrs -m 750 /var/lib/mrs-site/backups
install -d -o root -g mrs -m 750 /opt/mrs-site             # code (root-owned; app cannot rewrite itself)
install -d -o root -g mrs -m 750 /etc/mrs-site             # env file lives here, not in the repo
```

The app runs as `mrs` and **cannot modify its own code** — only its data directory.
That is deliberate: a compromised app cannot persist beyond `DATA_DIR`.

### 1.3 Install the code

```bash
# from your workstation
rsync -az --exclude node_modules --exclude data --exclude .env \
      ./mrs-site/ root@YOUR_SERVER:/opt/mrs-site/

# on the server
cd /opt/mrs-site
npm ci --omit=dev
node --version && node -e "require('better-sqlite3'); console.log('sqlite binding ok')"
```

**Verify:** `npm ci` finishes without native-build errors and the binding line prints.


Generate the two secrets **on the server** and paste them in:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # SESSION_SECRET
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"   # INTERNAL_WEBHOOK_SECRET
```

Why two: `SESSION_SECRET` signs cookies (browser-facing). `INTERNAL_WEBHOOK_SECRET` signs
machine calls between your backend and billing. Leaking one must not compromise the other —
separate keys, separate rotation.

**Verify:** `sudo -u mrs env $(cat /etc/mrs-site/app.env | xargs) node -e "console.log(process.env.SESSION_SECRET.length)"` → `64`.

### 2.2 Database, plans, admin

```bash
cd /opt/mrs-site
sudo -u mrs env $(cat /etc/mrs-site/app.env | xargs) node scripts/migrate.js
sudo -u mrs env $(cat /etc/mrs-site/app.env | xargs) node scripts/seed.js
sudo -u mrs env $(cat /etc/mrs-site/app.env | xargs) node scripts/create-admin.js you@yourdomain.com 'a long unique passphrase'
```

`migrate.js` is idempotent — safe to run on every deploy. It records applied files in

**Verify:**

```bash
sqlite3 /var/lib/mrs-site/site.db "select code,price_poisha from plans order by months;"
sqlite3 /var/lib/mrs-site/site.db "select email,role from users;"
```

Expect four plans (1/3/6/12 months) and one admin.

### 2.3 Machine keys for your site backend

Create one key per caller. Never one shared key: revocation must be surgical.

```bash
sudo -u mrs env $(cat /etc/mrs-site/app.env | xargs) \
  node scripts/create-api-key.js "existing-site payment" payments:write
sudo -u mrs env $(cat /etc/mrs-site/app.env | xargs) \
  node scripts/create-api-key.js "existing-site proxy" entitlement:read
sudo -u mrs env $(cat /etc/mrs-site/app.env | xargs) \
  node scripts/create-api-key.js "existing-site sync" catalog:write
```

Each prints `mrs_…` **once**. Store them in your site backend's secret store immediately;
only SHA-256 hashes are kept in the database.

You can also create and revoke keys later in the admin panel at `/admin/api-keys`.

**Verify:** call the internal API with each key and check the scope is enforced:

```bash
curl -s http://127.0.0.1:3100/api/internal/entitlement?email=you@yourdomain.com \
  -H "authorization: Bearer mrs_…"          # 200 + entitled:false
# the same call with the catalog:write key → 403 insufficient_scope  (correct)
```

Two units: the web process and the automation worker. They are separate so a slow backup
never delays a customer, and so the worker can be restarted without dropping sessions.

**Verify:**

```bash
curl -s http://127.0.0.1:3100/api/internal/ping        # {"ok":true,"time":"…"}
```

misconfigured. That refusal is a feature.

## Part 4 — Connect your existing site backend

There are two supported shapes. Pick one; do not mix per-endpoint.

### 4.1 Shape B — embedded (your backend is Node/Express)

Add three lines to your existing `server.js`. Order matters, and the library enforces it.

```js
const { mountBilling, attachProxyGate } = require('./mrs-site/src/integrations/mount');

// 1. BEFORE your routes that serve streams, and BEFORE your 404 handler
mountBilling(app, {
  basePath: '/billing',
  protectProxy: '/api/proxy',
  resolveUser: (req) => (req.user ? { id: req.user.id, email: req.user.email, role: req.user.role } : null),
  enableAdmin: true,
  enableApi: true,
});

// 2. your existing proxy handler, registered AFTER the gate
app.get('/api/proxy', myExistingProxyHandler);
```

If your proxy route is already registered earlier in the file and you cannot move it,
gate it in place instead:

```js
app.get('/api/proxy', ...attachProxyGate({ resolveUser }), myExistingProxyHandler);
```

`mountBilling` refuses to start in production if a route for `protectProxy` is already in
the stack — a gate that silently never runs is worse than a failed deploy.

**Verify:** see 8.4. **If it fails:** look for `mount.proxy_gate_shadowed` in the log; it
names the fix.

### 4.2 Shape A — sidecar (your backend is anything)

Your backend calls three endpoints over loopback. Your backend needs no new dependency,
language support, or library.

**Flow:**

```
customer pays on your site
      │
      ├─(1) POST /api/internal/orders              create the order, get the exact amount
      │
      ├─(2) your payment code verifies the TrxID   (bKash API / merchant API / human)
      │
      ├─(3) POST /api/internal/payment-confirmed   signed → fulfilled, code emailed, entitlement on
      │
      └─(4) GET  /api/internal/entitlement?userId=…   your proxy asks before every stream
```

**cURL reference (copy-paste):**

```bash
B=http://127.0.0.1:3100
KEY_PAY=mrs_…        # payments:write
KEY_READ=mrs_…       # entitlement:read

# (1) create an order
curl -s -X POST $B/api/internal/orders \
  -H "authorization: Bearer $KEY_PAY" -H 'content-type: application/json' \
  -d '{"email":"viewer@example.com","planCode":"1m"}'
# → 201 {"order":{"id":"ord_…","amount":500,"currency":"BDT","expiresAt":"…"}, …}

# (3) confirm the payment — sign the exact bytes you send
BODY='{"orderId":"ord_…","provider":"bkash","providerRef":"TRX8J2K9","amount":500,"currency":"BDT"}'
SIG="sha256=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$INTERNAL_WEBHOOK_SECRET" -r | cut -d' ' -f1)"
curl -s -X POST $B/api/internal/payment-confirmed \
  -H "authorization: Bearer $KEY_PAY" -H 'content-type: application/json' \
  -H "x-signature: $SIG" -d "$BODY"
# → 200 {"ok":true,"order":{"status":"fulfilled"},"issuedCode":"ABCD-EFGH-IJKL"}

# (4) the proxy's per-request question
curl -s "$B/api/internal/entitlement?userId=usr_…" -H "authorization: Bearer $KEY_READ"
# → {"entitled":true,"entitlement":{"active":true,"daysLeft":92,"endsAt":"…"}}
```

**Rules your backend must follow:**

| Rule | Why |
|---|---|
| Call `payment-confirmed` **only after** you have verified money arrived | it is the trust boundary; it does not check the money itself |
| Send the exact `amount` you were given | a mismatch is `409 amount_mismatch` and nothing is issued |
| Reuse the same `providerRef` on retries | that is what makes it idempotent — a retry cannot issue a second code |
| Treat a `200` with `issuedCode:null` as success | it means "already settled" |
| Never cache an `entitled:true` for more than ~30 s | expiry and refunds must bite |
| Cache `entitled:false` for no more than ~5 s | a just-paid customer must not be kept out |
| Time out the entitlement call at 1–2 s and **fail closed** | an open proxy is worse than a short outage |

Full contract, error codes and snippets for PHP/Python/Go: `docs/BACKEND-KNOWLEDGE.md`.
Machine-readable: `docs/openapi.yaml`.

### 4.3 Push your channel list in

```bash
curl -s -X POST $B/api/internal/channels/sync \
  -H "authorization: Bearer $KEY_SYNC" -H 'content-type: application/json' \
  -d @channels.json            # {"catalogId":"cat_…","channels":[{"name":…,"m3u8Url":…,"mirrors":[…]}], "replace":false}
```

Accepts your `/api/all-channels` payload shape as-is. The catalogue must carry a rights
attestation first (`/admin/catalogs`); otherwise the call is refused with
`400 catalog_required` and lists the catalogues you do have.

### 4.4 Players that cannot send cookies

```js
const { playUrlFor } = require('./mrs-site/src/integrations/signed-urls');
const url = playUrlFor({
  baseUrl: 'https://yoursite.com/api/proxy',
  targetUrl: channel.streamUrl,
  userId, channelId, ttlSeconds: 3600,

```

Mint it **after** the entitlement check, server-side. Tokens are HMAC-signed, bound to
user + channel, and expire.

## Part 5 — Automatic payment verification

This is the part that removes the human. It works in four layers; each is independent, so a
provider outage degrades instead of breaking.

### 5.1 Layer 1 — verify at submission

When the customer submits a TrxID, billing immediately asks the provider. If the answer is
"paid, exact amount", the order fulfils in that request and the customer sees their code
straight away. If the answer is "pending" or the provider is down, the payment stays queued
and layer 3 takes over.

Nothing to configure — it is automatic whenever a provider is configured.

### 5.2 Layer 2 — pick your provider

Set exactly one block in `/etc/mrs-site/app.env`, then `systemctl restart mrs-site mrs-worker`.

**bKash Tokenized Checkout (recommended in Bangladesh):**

```env
MFS_VERIFY_PROVIDER=bkash
BKASH_BASE_URL=https://tokenized.pay.bka.sh/v1.2.0-beta     # sandbox: https://tokenized.sandbox.bka.sh/v1.2.0-beta
BKASH_APP_KEY=…
BKASH_APP_SECRET=…
BKASH_USERNAME=…
BKASH_PASSWORD=…
BKASH_USE_PAYMENT_QUERY=0
```

Two modes:
- `BKASH_USE_PAYMENT_QUERY=0` → queries by the **TrxID the customer typed**. This is the right
  mode for a plain merchant number, and the only one where you never had to create the
  payment yourself.
- `BKASH_USE_PAYMENT_QUERY=1` → queries by `paymentID`. Use this if your checkout creates the
  payment through the bKash API rather than a manual send-money.

Getting these credentials requires a bKash merchant account and their onboarding
(sandbox first, then production). Tokens are cached and refreshed a minute before expiry —
if bKash rotates them you will not see a failed payment.

**Nagad merchant API:**

```env
MFS_VERIFY_PROVIDER=nagad
NAGAD_VERIFY_URL=https://…        # from your merchant agreement
NAGAD_MERCHANT_ID=…
NAGAD_MERCHANT_PRIVATE_KEY=/etc/mrs-site/nagad-private.pem
```

The request is RSA-SHA256 (PSS) signed with your merchant key. Nagad's endpoint names vary
per agreement; if yours differs from the common shape, keep `NAGAD_VERIFY_URL` pointing at
a 40-line middleware you control that speaks Nagad and answers:

```json
{ "status": "success", "amount": 500.00, "currency": "BDT", "reference": "…" }
```

Then set `MFS_VERIFY_PROVIDER=generic` and point `MFS_VERIFY_URL` at it. That is the
supported escape hatch and it is what most operators end up doing.

**Any other rail (own middleware, bank transfer matcher, SMS parser):**

```env
MFS_VERIFY_PROVIDER=generic
MFS_VERIFY_URL=https://your-middleware.internal/verify
MFS_VERIFY_TOKEN=…
```

Your middleware receives `{"trxId":"…","amount":500,"currency":"BDT"}` and answers
`{"status":"success","amount":500,"currency":"BDT","reference":"…"}` for a real payment,
anything else otherwise. `status:"pending"` is meaningful: billing will retry it later.

### 5.3 Layer 3 — the reconciler

`scripts/worker.js` runs every `WORKER_RECONCILE_MS` (default 60 s) and re-asks about every
pending payment. This is what makes the system automatic for the customer who pays and
closes the tab, and for the outage where the provider was down at submission time.

```env
WORKER_RECONCILE_MS=60000
RECONCILE_MAX_ATTEMPTS=12        # stop asking after 12 tries (~12 minutes of retries)
RECONCILE_MAX_AGE_HOURS=72       # and never about anything older than 3 days
```

Attempts and the last refusal reason are recorded on the payment row, visible in the admin
queue — so "why is this payment still pending?" always has an answer.

**Verify the whole path without real money.** Point the verifier at a fake provider, submit a
payment, and watch it fulfil on its own:

```bash
node -e "
const http=require('http');
let n=0;
http.createServer((q,s)=>{s.setHeader('content-type','application/json');
  s.end(JSON.stringify(++n<2?{status:'pending'}:{status:'success',amount:500,currency:'BDT',reference:'FAKE-1'}));
}).listen(4599,()=>console.log('fake provider on 4599'));" &
MFS_VERIFY_URL=http://127.0.0.1:4599 MFS_VERIFY_PROVIDER=generic \
  node scripts/worker.js --job=reconcile
```

The repository's own test does exactly this and asserts: first answer pending → order stays
`awaiting_verification`; second answer success → order `fulfilled` with exactly one code;
a third pass issues nothing. A provider that reports the wrong amount **never** fulfils.

### 5.4 Layer 4 — the human, where a human is still right

Manual approval is not removed, it is demoted: it is the fallback when no provider can
answer. `/admin/payments` shows the queue with the TrxID, sender hint, amount and last
verification reason. Approving goes through the same `confirmPayment` as the automatic path,
so it is equally idempotent and equally audited.

**Decide by this table:**

| Situation | What happens |
|---|---|
| Provider confirms, amount exact | fulfilled in the request |
| Provider says pending | queued, reconciler retries for 12 attempts |
| Provider says success, amount short | **never** auto-fulfils; stays queued with `amount_mismatch` |
| Provider unreachable | queued; reconciler retries; customer sees "verifying" |
| Provider has no such TrxID after max attempts | stays queued for a human; visible in the queue |
| Customer paid twice | second TrxID is rejected by the provider ref uniqueness — no double subscription |
| Customer disputes after fulfilment | refund path: `/admin/orders`, then revoke the code / entitlement (audited) |

### 5.5 What is deliberately *not* automatic

Refunds. A human decides, because a wrong automatic refund is money gone. The system
records everything needed to make it a one-minute decision (`/admin/orders`, `/admin/audit`),
but it will not move money outward on its own.

## Part 6 — Everything else, automatically

`scripts/worker.js` is the daemon. Every job is independent, wrapped, logged, and safe to
re-run.

| Job | Default interval | What it does | Why it must exist |
|---|---|---|---|
| `reconcile` | 60 s | re-verifies pending payments | Part 5 |
| `expireOrders` | 5 min | orders past TTL → `expired` | a stale checkout must not be fulfilled weeks later |
| `purgeSessions` | 1 h | deletes expired sessions | the table cannot grow forever |
| `backup` | 24 h | `VACUUM INTO` a copy, keep 14 | one disk error must not erase every subscription |
| `doctorSync` | 10 min | applies the channel health report | dead channels leave the list without a human |
| `housekeeping` | 1 h | audit retention + heartbeat file | monitoring, and a bounded audit log |

All intervals are env-tunable (`WORKER_*_MS`). Cron instead of a daemon is equally
supported:

```cron
* * * * * cd /opt/mrs-site && set -a && . /etc/mrs-site/app.env && set +a && /usr/bin/node scripts/worker.js --job=reconcile  >> /var/log/mrs/worker.log 2>&1
*/5 * * * * cd /opt/mrs-site && set -a && . /etc/mrs-site/app.env && set +a && /usr/bin/node scripts/worker.js --job=expireOrders >> /var/log/mrs/worker.log 2>&1

```

### 6.1 Email

`MAIL_DRIVER=smtp` and the worker inside the web process sends from the outbox with retry
and exponential backoff (`MAIL_MAX_ATTEMPTS`, `MAIL_POLL_MS`). In development,
`MAIL_DRIVER=dev` writes `.eml` files to `$DATA_DIR/outbox` instead — that is how you test
activation mail without a mailbox.

Deliverability (SPF, DKIM, DMARC, warmup) decides whether codes reach inboxes. Follow
`../m3u-doctor/docs/EMAIL-SETUP.md`, then check mail-tester before taking money.

**Verify:**

```bash
ls -t /var/lib/mrs-site/outbox | head          # dev driver
grep -c "status.*failed" /var/lib/mrs-site/site.db  # or: sqlite3 site.db "select status,count(*) from outbox group by status"
```

### 6.2 Channel health

```env
DOCTOR_REPORT=/var/lib/m3u-doctor/report.json
```

The worker applies it every 10 minutes: dead → hidden, recovered → back. Only
`health_status='alive'` rows in `status='active'` catalogues are ever served, and no row is
ever deleted — "dead" is a state, not a loss.

### 6.3 Backups and the restore drill

Backups land in `$DATA_DIR/backups` (14 kept). **A backup you have never restored is not a
backup.** Do this once, on the real server:

```bash
systemctl stop mrs-site
cp /var/lib/mrs-site/backups/$(ls -t /var/lib/mrs-site/backups | head -1) /tmp/restore-test.db
sqlite3 /tmp/restore-test.db "select count(*) from users; select count(*) from orders; select count(*) from entitlements;"
# non-zero for each → the file is intact
DATA_DIR=/tmp/restore-drill DB_FILE=/tmp/restore-test.db node /opt/mrs-site/scripts/migrate.js
systemctl start mrs-site
rm /tmp/restore-test.db
```

Also copy `/var/lib/mrs-site/backups` off the machine (object storage, another host) — a
backup on the same disk does not survive the failure it exists for.

### 6.4 Monitoring

```bash
# uptime: unauthenticated and content-free
curl -fsS https://billing.yourdomain.com/api/internal/ping    # via loopback only in prod
curl -fsS http://127.0.0.1:3100/api/internal/ping

# detailed (needs channels:read)
curl -s http://127.0.0.1:3100/api/internal/health -H "authorization: Bearer mrs_…"

# worker alive?
cat /var/lib/mrs-site/worker-heartbeat.json
```

Point your monitor at these three plus disk space. Alert on: non-200, heartbeat older than
15 minutes, and `data/site.db` growing past 80 % of disk.

## Part 7 — Full control of the site

Everything an operator needs is a click or one command. Nothing requires a redeploy.

| I want to… | Where | Notes |
|---|---|---|
| Change a plan's price | `/admin` → plans (or DB `plans`) | money is integer minor units (`price_poisha`) — never floats |
| See who paid and what they got | `/admin/orders`, `/admin/payments`, `/admin/audit` | every money action is audited with actor |
| Approve/reject a manual payment | `/admin/payments` | goes through the same idempotent confirm path |
| Revoke an activation code | `/admin/codes` | revoking a redeemed code removes no access — use entitlements for that |
| Look up a subscription | `/admin` → users, or `GET /api/internal/entitlement?email=` | returns `daysLeft` |
| Cancel access | `node scripts/revoke-access.js --email … --reason "…"` | audited; the gate refuses on the next request. `--dry-run` first if you like |
| Add/edit an ad | `/admin/ads` | stored server-side, weighted, impression + click counts |
| Create a catalogue | `/admin/catalogs` | requires rights attestation: basis, counterparty, licence ref, territory, validity |
| Publish / pause a catalogue | `/admin/catalogs` → confirm → activate/pause | pause removes every channel in it from the site instantly |
| See dead channels | `/admin/channels?health=dead` | no rows are ever deleted |
| Manage machine keys | `/admin/api-keys` | create with scopes, plaintext shown once, revoke instantly |
| Change payment numbers | env `BKASH_NUMBER`/`NAGAD_NUMBER` + restart | shown on the payment page |
| Change the SMTP provider | env + restart | outbox retries automatically |
| Read what happened at 14:32 | `/admin/audit` | or `journalctl -u mrs-site` |

The site itself (public pages) is server-rendered from `src/views/*` and styled by
`public/css/app.css` — one file to rebrand, no build step.

## Part 8 — Go live, and prove it

### 8.1 Pre-flight

```bash
cd /opt/mrs-site
npm test                    # 47/47 — the money path, the gate, the host-app mount
npm run audit               # 181 checks against the running site
npm run bench               # 12,000-channel query timings
```

`npm run audit` needs the site running and an admin; it is a real crawl, so run it against
staging or production, not a laptop-only instance.

### 8.2 Publish the catalogue

```bash
# 1. create with a real rights record in /admin/catalogs, confirm it, activate it
# 2. ingest it
sudo -u mrs env $(cat /etc/mrs-site/app.env | xargs) node scripts/ingest.js --all
# 3. or sync from your existing site
curl -s -X POST http://127.0.0.1:3100/api/internal/channels/sync -H "authorization: Bearer mrs_…" ...
```

Ingest refuses a catalogue without an attestation, and refuses a blocked host. That refusal
is the audit trail for what you sell and on what basis. Keep it on.

### 8.3 Money path, with real (small) money

Do this once with the smallest plan and a real bKash send:

1. Register a fresh account on the site.
2. Choose 1 month → pay the exact amount to the bKash number shown.
3. Paste the TrxID → the page should show **"verifying"**, then within one reconcile cycle
   (≤ 60 s) the account shows **active**, and the activation email arrives.
4. Check `/admin/orders` — status `fulfilled`, one code, `verified_by` starts with `auto:`.
5. Check the code was emailed (`/admin/audit`, or the outbox in dev).

If step 3 never resolves: `/admin/payments` shows the reason. `amount_mismatch` means the
amount sent differed; `bkash_status:…` means bKash says it is not completed yet.

### 8.4 Gate proof, against your real proxy

```bash
# anonymous → must be refused
curl -si 'https://yoursite.com/api/proxy?url=https://your-cdn/live.m3u8' | head -1     # 401
# logged in, unpaid → refused
curl -si -b cookies.txt 'https://yoursite.com/api/proxy?url=…' | head -1               # 402
# paid viewer, channel in catalogue → 200; and any other URL → 404 channel_unavailable
```

That last one matters: it proves the proxy is not an open relay.

### 8.5 Checklist — do not take money until every line is true

- [ ] `SESSION_SECRET` and `INTERNAL_WEBHOOK_SECRET` are 32+ random bytes and differ
- [ ] `/api/internal/*` is refused from the internet (`curl` from your laptop → 404)
- [ ] HTTPS with HSTS; `PUBLIC_URL` is `https://`
- [ ] One API key per caller; proxy key has only `entitlement:read`
- [ ] `REQUIRE_LICENSE_ATTESTATION=1`, catalogue has a real licence reference
- [ ] `BLOCKED_SOURCE_HOSTS` still contains the reseller hosts
- [ ] One real small payment completed end to end, automatically
- [ ] Activation email arrives in an inbox (not spam), code redeems
- [ ] Guest and unpaid users cannot reach a stream URL (8.4)
- [ ] A backup exists, and you have restored one (6.3)
- [ ] Monitor watching `/ping` and the worker heartbeat
- [ ] Admin password is unique and long; admin panel behind HTTPS only
- [ ] `data/` contains no demo state (`npm run reset-data -- --yes --seed` on the target dir)

## Part 9 — Operating it

**Daily (2 minutes):** dashboard `/admin` — pending payments, failed emails, dead channels.
`/admin/payments` should normally be empty; if it is not, read the reason column.

**Weekly:** `journalctl -u mrs-site --since "7 days ago" | grep '"level":"error"'`,
disk space, backup list, and one random restore of a code (does it redeem? it should say
already used — that proves the hash path works).

**Monthly:** rotate `INTERNAL_WEBHOOK_SECRET` (create the new value, deploy both sides
together, revoke old keys), review `/admin/api-keys` for keys nobody uses, review
`/admin/audit` for anything unexplained, `certbot renew --dry-run`.

**Incident: subscription active but stream refused.** Check the entitlement row
(`/admin` → user), then the gate log line `proxy_gate.unknown_target` (URL not in catalogue)
vs `authentication_required` (cookie not recognised — usually the host app's session, see
`resolveUser`).

**Incident: payments stuck pending.** `/admin/payments` reason column → provider status.
If the provider is down, leave it: the reconciler retries for 12 attempts and then parks it
for a human. Do not bulk-approve — that is how fraud gets in.

**Incident: disk full.** Backups are the usual culprit; `BACKUP_KEEP` and the `backups/`
directory. Then `sqlite3 site.db "PRAGMA wal_checkpoint(TRUNCATE);"`.

**Cancelling access (refund, chargeback, abuse):**

```bash
node scripts/revoke-access.js --email viewer@example.com --dry-run     # show what would go
node scripts/revoke-access.js --email viewer@example.com --reason "refund REF-1042"
```

History is kept: orders, payments, codes and the user are untouched, so "why did this person
lose access?" is answerable from `/admin/audit` forever.

**Rollback:** keep the previous release directory, `systemctl stop`, swap the symlink, run
`migrate.js` (forward-only, idempotent), `systemctl start`. Migrations never drop columns;
rollback of code with a newer schema is safe, rollback of schema is not — that is why it is
forward-only.

## Part 10 — When you outgrow one machine

In order, and only when the measurement says so:

1. **Vertical first.** SQLite handles a very large multiple of what one IPTV site does; the
   12,000-channel bench (Part 8.1) shows the ceiling is not the database.
2. **Split the worker** onto its own host, pointing at the same file over a shared volume —
   or move to Postgres and run N workers.
3. **Postgres** when you need more than one app instance: translate `001_init.sql` (`TEXT`
   ids, integer minor units, ISO timestamps map directly), keep the same models.
4. **Redis** for rate limits and sessions the moment you run more than one instance —
   the in-memory limiter is per-process by design and documented as such.
5. **Never** put the stream proxy in front of a shared cache without the entitlement check
   inside it.
